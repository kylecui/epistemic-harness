## 3. 独立 lab 实例设计（与工作网关完全隔离）

```
harness-backend（工作）  :8787  quota_policy.yaml       traces/
harness-backend-lab      :8788  quota_policy.lab.yaml   traces-lab/   env_file: .lab.env
```

- `docker-compose.lab.yml`：同一镜像、不同容器名/端口/策略/账本目录；lab 策略只含
  硅基流动池（受试 + 裁判两模型），**硬预算封顶**（借鉴 tokenplus 的 key 级限额）。
- runner：`--gateway-url http://127.0.0.1:8788`，模型名取自 lab 策略；A0 直连硅基流动。
- campaign 跑在 lab 沙箱容器内（issue #13 的容器平面），结果回写工作树。
- 收益：零资源干扰；账本/冷却/路由状态与工作实例物理分离；实验可随时重置。

## 4. tokenplus.cn 借鉴（docs 2026-11-24 读取：快速入门/功能总览首页）

其定位「一站式 Token 智能调度平台」= 我们网关的产品化同类：统一 API、多服务商同模型
实时比价 + 故障切换、BYOK、项目空间（**每把 API key 可设消费限额与到期**）、
零数据留存（ZDR）开关、用量/调用/输入输出日志。

**值得借鉴（工程，非研究）**：
1. **key/项目级预算封顶 + 到期**——我们只有池级配额，缺「本次活动最多花 ¥X」的硬封顶；
   lab 策略直接加入。
2. **同模型多服务商比价路由**——我们的池是服务商粒度；模型粒度的跨商 failover 是
   合理扩展（DeepSeek-V4-Flash 在硅基/TokenPlus 间择优）。
3. **ZDR 开关**——实验涉及仓库数据时，traces 需要「不落原文」模式。

**与论文的关系**：tokenplus 治理的是 L4（预算/权限/路由）——可作为 Paper 1.5 的
「意图层治理已产业化」先例引用；它**没有**任何认识论分层或结构化 interim 的概念，
Paper 2/3 的新颖性不受影响。
