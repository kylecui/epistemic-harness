双维治理 Harness v2：双系统认知光谱、双协议多端接入与 Pi 洁净室落地

本蓝图将卡尼曼《思考，快与慢》的认知光谱（System 0–2+）与五层认识论模型（L1–L5）融合为统一运行时，并通过标准 MCP Server + 本地 LLM 代理网关双协议实现跨终端（Pi、OpenCode、Claude Code、Codex、Antigravity 等）免适配通吃。演进路径采用 Phase 0（Gemini Gem 软协议 POC）→ Phase 1（Pi 洁净室硬插件落地）→ Phase 2（全终端代理熔断）。

双系统认知光谱

直觉归探索，理性归裁决

承认 System 1 直觉与 L3 经验在快速探索中的价值，但在 System 2 理性推导中强制启用 L1 公理与短板继承，熔断 “Aha → Wait, but wait” 思维空转。

双协议多端通吃

MCP 管知识，Proxy 管推理

不做任何终端的 Case-by-Case 硬编码适配。MCP 统一承接知识隔离与 DAG 审计，本地 API 代理网关统一接管推理档位与流式熔断。

洁净室演进

Gem 试协议，Pi 建内核

先用 Gemini Gem 跑通测试与开发闭环并攒下失败用例；Phase 1 选极简开源终端 Pi 避开日常 OpenCode/OmO 插件干扰，验证成熟后再无缝回接多端。

将《思考，快与慢》的认知光谱与 L1–L5 认识论深度耦合

人类面对不同场景并不会只有“不思考”和“拼命思考”两档，而是从条件反射、直觉模式识别，逐步过渡到受控启发式、第一性原理推导与元认知复核。Harness 将这两套体系耦合在一起：允许 System 1 在探索期借用 L3 经验快速筛选方向，但强制 System 2 在收敛裁决期切换为 L1 公理 + L2 一手证据，且由代码执行“短板继承原则”——只要中间推导（L5）引用了 L3 经验，结论置信度上限就永久锁定在 L3。

认知等级（双系统光谱） 推理档位 允许动用的认识论层级 典型工作流场景 升档与防震荡约束
System 0 · 条件反射 R0 零推理 L4 明确指令 肌肉记忆式原子动作、明确命令翻译、固定模板转换 关闭思考链；禁止自我加戏，仅在报错时升档
System 1 · 直觉判断 R1 低推理 L2 检索 + L3 经验（快速启发） 常规 Sub-Agent 信息取证、方向初筛、模式匹配 允许用 L3 提出直觉假设，但强制标记 provisional
System 1.5 · 受控启发 R2 中推理 L1 + L2 + 带反证边界的 L3 多文件/多源比对、常规排障、L5 中间推导构建 强制输出结构化 JSON 与 source_ids；开启震荡监测
System 2 · 理性推导 R3 高推理 L1 一票否决 + L2 一手证据 第一性原理推演、跨源矛盾裁决、高风险方案权衡 严禁将 L3 当公理；触发 Wait, but wait 空转即转外部求证
System 2+ · 元认知审视 代码 / 独立 Critic 全量 DAG 审计 + 人类裁决 验证推导链是否越级、检查盲区、L3/L5 知识升格 PR 物理脱离主模型上下文，由确定性代码或独立审视者完成

双协议多端接入：MCP 管知识面，本地代理网关管推理面

为了同时兼容 Pi、OpenCode、Claude Code、Codex、Antigravity、WorkBuddy、ZCode 等终端，绝不能针对每个终端的私有插件 API 写一套核心逻辑。架构上必须把治理能力拆成两条与终端无关的标准总线：

  • 知识与审计总线（Standard MCP Server）：承载 L1/L2/L3 隔离库、L5 中间推导暂存与确定性 DAG 校验。任何支持 MCP（stdio 或 Streamable HTTP）的终端即插即用。
  • 推理与熔断总线（Local LLM Proxy Gateway）：由于 MCP 无法控制宿主 Agent 的 reasoning_effort 或截断内部思考流，我们在本地起一个兼容 OpenAI / Anthropic 协议的轻量代理，各终端只需把 baseUrl 指向本地网关，即可统一实现自适应档位路由、思考预算硬顶与流式震荡熔断。
  • 单一规范源（harness.yaml）：所有 L1 规则、认知路由策略与软提示模板只写一份，通过极薄的编译脚本同步生成各端的 AGENTS.md、CLAUDE.md 或 Gemini Gem 指令。

三阶段“测试 ↔ 开发”演进路线：从 Gemini Gem 到 Pi 洁净室

避免一开始就陷入重型基础设施开发。先用零代码成本的 Gemini Gem 验证认知与认识论协议，再用极简洁净的开源终端 Pi 落地硬插件内核，最后向日常主力工具推广。

PHASE 0 · 协议探索期

Gemini Gem（Skills）POC

用纯软提示跑通 L1–L5 分层、System 0–2 认知切换与输出契约。核心产出不是“完美遵守”，而是收集软约束守不住的真实翻车样本（Golden Test Set），直接转化为 Phase 1 插件的验收测试。

PHASE 1 · 硬内核洁净室

Pi CLI + MCP Server

在无历史插件干扰的 Pi 洁净环境中，开发 epistemic-mcp 服务器与 harness.yaml 编译器；利用 Pi 原生 MCP 支持与 JSON/RPC 非交互模式跑自动化回归测试。

PHASE 2 · 全端硬推理闭环

本地 Proxy 网关 + 多端回接

上线本地 LLM 代理网关接管自适应推理与流式震荡熔断；将同一套 MCP + Proxy 接入日常 OpenCode、Claude Code、Codex 等多端，完成全工作流闭环。

Phase 1 细化设计：为什么选 Pi 作为洁净室以及具体落地方案

你日常使用的 OpenCode 往往挂载了大量编排插件（如包含 30+ 生命周期钩子与多 Agent 路由的 Oh-My-OpenAgent），在上面直接调试新 Harness 会面临严重的钩子冲突、路由覆盖和日志污染。 相比之下，开源终端 Pi Coding Agent（@earendil-works/pi-coding-agent）是一个极简内核——默认仅内置 read、write、edit、bash 四个基础工具，不强加复杂的内建规划模式或子代理路由，同时从 v0.99.0 起原生支持标准 MCP（~/.pi/agent/mcp.json / 项目级 .pi/mcp.json）、支持通过 ~/.pi/agent/models.json 自定义网关 baseUrl，并提供 print / JSON / RPC 四种运行模式，天然适合做自动化回归测试的洁净室。

Phase 1 核心组件 具体实现形态 与 Pi 的标准对接方式 解决的硬约束问题
knowledge/ 分域库 本地 Git 仓库 + 轻量 SQLite FTS 索引，物理拆分为 l1_axioms/、l2_library/、l3_heuristics/ 不让 Pi 直接 read 混读，而是通过 MCP 工具按域检索并返回强制元数据头 物理隔离公理、证据与经验；L3 条目强制绑定 counter_examples 字段
epistemic-mcp 轻量 TypeScript 或 Python（FastMCP）本地 MCP Server（stdio 传输） 写入项目根目录 .pi/mcp.json（与 Claude Desktop / OpenCode 同格式） 暴露 6 个硬工具：query_l1、search_l2、recall_l3、submit_l5_claim、audit_dag、propose_promotion
provenance-dag 引擎 内嵌在 epistemic-mcp 内的纯代码有向无环图校验器 当 Pi 调用 submit_l5_claim 时同步拦截校验，不合法直接返回 Tool Error 核验 source_ids 真实存在；纯代码执行短板降级 min(upstream_tiers)，杜绝经验洗白
harness-compiler 极简 CLI 脚本，读取单一规范 harness.yaml 生成 Pi 项目级 AGENTS.md 与 .pi/skills/ 软协议（后续同步生成 Gem / OpenCode 配置） 保证双系统认知路由规则与 L1–L5 术语在多端完全一致，杜绝漂移
eval-runner 回归框架 调用 Pi 的非交互 print / JSON 模式批量回放 Phase 0 黄金测试集 直接读取每次会话的 MCP DAG 审计日志与 Tool Call 序列做自动化断言 量化验证“经验越级拦截率”与“低推理任务零冗余率”，驱动持续迭代

Phase 1 最小可行目录骨架（洁净室仓库布局）

整个 Phase 1 可以在一个独立的本地 Git 仓库中启动，不污染任何现有工作环境，同时保证未来无缝迁移到 OpenCode：

epistemic-harness/
├── harness.yaml                # 单一规范源：L1–L5 规则、System 0–2 策略、Schema 定义
├── knowledge/                  # 物理隔离的知识域（Git 版本化）
│   ├── l1_axioms/              # 只读公理与硬约束
│   ├── l2_library/             # 带来源与时间戳的外部证据索引
│   └── l3_heuristics/          # 经验法则（强制含 scope 与失效反例字段）
├── mcp-server/                 # 标准 MCP Server（stdio / Streamable HTTP）
│   ├── tools_epistemic.py      # query_l1 / search_l2 / recall_l3
│   ├── dag_engine.py           # submit_l5_claim / 短板继承计算 / L1 冲突检测
│   └── promotion_gate.py       # 人类 PR 升格队列
├── proxy-gateway/              # Phase 2 预留：本地 OpenAI/Anthropic 代理 + 震荡熔断
├── clients/                    # 由 harness.yaml 自动编译的极薄适配层
│   ├── gemini-gem.md           # Phase 0 软规范
│   └── pi/                     # .pi/mcp.json + AGENTS.md + models.json 模板
└── evals/                      # Phase 0 攒下的黄金测试用例与自动化断言脚本

Phase 2 扩展：接入本地代理网关与回接日常主力终端

当 Phase 1 在 Pi 洁净室里跑通全部黄金测试后，Phase 2 只需在 proxy-gateway/ 中挂载一个轻量代理（例如基于 LiteLLM 或自研 FastAPI/Hono 中间件），并将 Pi 的 ~/.pi/agent/models.json 以及 OpenCode、Claude Code 的自定义 baseUrl 指向本地端口（注意 Pi 对原生 Anthropic 通道会自动拼接 /v1/messages，代理路径需止于 /anthropic）。届时，无需改动任何终端插件，即可全局启用自适应推理路由与流式认知震荡熔断。

先在 Gemini Gem 里用最低成本把认识论与双系统协议跑顺，再把软规则“守不住”的边界案例，逐一编译进 Pi 洁净室的硬性插件与代理网关。
